# Seeding: Images & Firestore Data

## Overview

Travel catalog images and data are stored separately from the frontend SPA:

| Asset | Storage | Access |
|-------|---------|--------|
| Images (JPG/PNG) | Private GCS bucket `{project}-media-{env}` | Signed URLs (time-limited, generated by backend) |
| Catalog data | Firestore collections | Backend API |
| Frontend SPA | Public GCS bucket `{project}-frontend-{env}` | Public read |

**Images are not included in this repository — bring your own.** The bucket is private, so objects are not publicly accessible; the backend serves them via signed URLs.

---

## Image Bucket

### Bucket name

```
{GCP_PROJECT_ID}-media-{ENVIRONMENT}
```

e.g. `my-gcp-project-media-prod`

### Manual image upload

To upload (or refresh) images from your local clone:

```bash
# Authenticate
gcloud auth application-default login

# Sync — mirrors frontend/public/img/ into gs://{bucket}/img/
gsutil -m rsync -r -d frontend/public/img gs://{MEDIA_BUCKET_NAME}/img
```

The `-d` flag deletes GCS objects that no longer exist locally. Omit it if you want to upload without removing anything.

To upload a single subdirectory:

```bash
gsutil -m rsync -r frontend/public/img/accommodations \
  gs://{MEDIA_BUCKET_NAME}/img/accommodations
```

### IAM requirements for upload

The identity running `gsutil` needs `roles/storage.objectAdmin` on the media bucket. The `cb-content-build` Cloud Build service account already has this role (provisioned by Terraform).

For a personal upload, grant yourself the role:

```bash
gcloud storage buckets add-iam-policy-binding gs://{MEDIA_BUCKET_NAME} \
  --member="user:{YOUR_EMAIL}" \
  --role="roles/storage.objectAdmin"
```

## Firestore Seeding

### Collections

| Collection | Source file | Reseed behavior |
|------------|-------------|-----------------|
| `accommodations` | `backend/data/accommodations.json` | Wiped + reloaded |
| `restaurants` | `backend/data/restaurants.json` | Wiped + reloaded |
| `flights` | `backend/data/flights.json` | Wiped + reloaded |
| `experiences` | `backend/data/experiences.json` | Wiped + reloaded |
| `users` | `backend/data/users.json` | **Never touched by seeder** |
| `applications` | `backend/data/applications.json` | **Never touched by seeder** |

### How image URLs are stored

The seeder writes the object path relative to the bucket root, e.g.:

```
img/accommodations/acc-arg-001.jpg
```

No signed URL is stored. At read time, the backend service layer calls `storage_client.resolve_image_url()` which generates a V4 signed URL with a configurable TTL (default: 60 minutes, controlled by `SIGNED_URL_TTL_MINUTES` env var on Cloud Run).

External URLs (e.g. flight airline logos starting with `https://`) are stored and returned unchanged.

### Seeding via Cloud Build (production / GCP)

The `content-seed-{env}` Cloud Build trigger fires automatically when changes are pushed to `main` in:

- `backend/data/**`
- `frontend/public/img/**`
- `backend/scripts/**`

It runs `backend/cloudbuild.content.yaml`, which:
1. Syncs images to the media bucket (`gsutil rsync`).
2. Executes the `firestore-seeder-{env}` Cloud Run Job, which upserts catalog data.

To trigger it manually from the GCP console: Cloud Build → Triggers → `content-seed-prod` → Run.

### Seeding locally (development)

Requires Application Default Credentials with Firestore write access:

```bash
gcloud auth application-default login

# From the repo root
export GOOGLE_CLOUD_PROJECT=your-gcp-project-id
export MEDIA_BUCKET_NAME=your-gcp-project-id-media-prod  # optional; only affects logging

cd backend
python scripts/seed_firestore.py
```

The script adds `backend/` to `sys.path` automatically so models are importable.

### Seeding users

Users are **not** seeded by this script. To populate Firestore `users` collection from `backend/data/users.json`, run the one-time migration separately:

```bash
cd backend
python scripts/migrate_users.py   # (create this script if needed)
```

Or import directly from the GCP Console → Firestore → Import/Export.

## Signed URL TTL

Signed URLs expire after `SIGNED_URL_TTL_MINUTES` (default: 60 minutes). The TTL is set as a Cloud Run environment variable via Terraform variable `signed_url_ttl_minutes`.

Clients that cache API responses longer than the TTL will see broken images. The recommended pattern is to re-fetch the item when an image fails to load (the `<img>` `onError` handler can trigger a re-fetch of the item endpoint).

## Troubleshooting

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| Images return 403 | Signed URL expired, or Cloud Run SA lacks `objectViewer` on media bucket | Re-fetch item; verify IAM |
| Images return 404 | Object path in Firestore doesn't match bucket layout | Re-run image sync + seeder |
| Seeder job fails | Cloud Run Job image is stale (no `scripts/` dir) | Rebuild + push backend image, then re-execute job |
| Signed URL generation fails with `SigningError` | SA missing `iam.serviceAccountTokenCreator` on itself | Re-apply Terraform (`service_accounts` module) |
